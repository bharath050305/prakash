# Prakash: Smart Streetlight Maintenance and Decision Support System

NLP course project · Group 6 · SDG 11 (Sustainable Cities and Communities)
**Team:** Gregory, Bharath Rathinasabapathy, Harshwardhan Ahire

## The problem

Faulty streetlights reported by citizens are still processed by hand. That means delayed repairs, inefficient maintenance scheduling and more risk to public safety.

## What this project does

Prakash is a full-stack web application (Python backend, real database, live updates, three user roles) that takes a complaint from any channel and carries it all the way to a fixed lamp:

| Step | What happens | Technique |
|---|---|---|
| 1. Collect | WhatsApp, SMS, email, X/Twitter, call-centre transcripts, web portal (with photo, GPS pin and voice input), bulk CSV | Channel webhooks + channel-specific text clean-up |
| 2. Understand | Language (English, Hindi, Marathi, Hinglish), fault type (8 classes), entities (pole ID, landmark, road, sector, duration, fault phrase), severity 0–100 with a reason for every point | TF-IDF + logistic regression, rule/gazetteer NER, explainable scoring |
| 3. Locate | Geocode, snap to the nearest lamp, merge duplicate reports into one ticket | GIS maths (haversine), pole-ID lookup |
| 4. Decide | Hotspot clusters, 14-day lamp failure risk, weekly fault forecast, crew routes that respect skills and shift length | DBSCAN, gradient boosting, damped Holt smoothing, insertion + 2-opt/or-opt routing |
| 5. Act | Live dashboard and alerts, auto-dispatch of critical faults, technician mobile route, automatic replies and status updates to citizens, human review queue that retrains the model | Server-sent events, human-in-the-loop learning |

## Roles

| Role | Can do |
|---|---|
| **Citizen** | Register, report a fault with a live "what the AI understood" preview, confirm an existing fault instead of duplicating it, track progress, rate the repair, see the public city map, get notifications |
| **Technician** | See an optimised route, start and complete jobs with notes and parts, toggle shift, see history and ratings |
| **Admin** | Everything else: live dashboard, ticket management, review queue, NLP lab, channels simulator, hotspots, predictive maintenance (with a rainfall what-if), crew scheduling and dispatch, analytics, model metrics and retraining, team and access, audit log, settings, CSV import/export |

Access is enforced on the server for every API route, not just hidden in the UI (see `tests/test_api.py`).

## Run it

You need Python 3.10+ (developed on 3.13). Open a terminal in this folder.

```bash
pip install -r requirements.txt
python run.py
```

Then open **http://localhost:5000**.

The first start takes about 10 seconds: it trains the models and generates the demo data. After that it starts in about 3 seconds.

Useful options:

```bash
python run.py --reset                # wipe the database and regenerate fresh demo data
python run.py --host 0.0.0.0         # let phones on the same Wi-Fi open it (http://<your-PC-IP>:5000)
python run.py --port 8080            # use another port
python -m pytest tests -q            # run the automated tests (24 tests)
python tests/smoke_api.py            # end-to-end API check against a running server
```

Demo accounts are listed on the sign-in page (one click each for Admin, Citizen and Technician). They are created from `backend/seed.py`. **Change or remove them before any real deployment.**

The app works offline except for the map background tiles and the web fonts. Charts, icons, map markers and all logic are bundled locally.

## Honest scope and limitations

* There is no public labelled streetlight-complaint dataset. **Training complaints, the lamp network, 12 weeks of history, ratings and accounts are synthetic**, generated by this project.
* The classifier is evaluated on wording it never saw in training (held-out paraphrases) and on 24 hand-written messages, and compared with the keyword-rule approach of the first prototype. Those numbers show the pipeline works; they are **not** a promise about real citizen messages. Retrain on real labelled complaints before deployment. The Models page shows every number, the confusion matrix and the errors.
* Severity is a transparent rule-weighted score rather than a trained model, on purpose, so every point can be explained.
* Channels are simulated through real webhook endpoints (`/api/intake/<channel>`); connecting a WhatsApp/SMS provider means pointing it at those URLs.
* Map geometry uses approximate real coordinates for Navi Mumbai. Lamp positions are generated.
* Built on Flask's development server, which is fine for a demo. Use a production WSGI server, HTTPS and real secrets to deploy.
